# สัญญาเรื่องสิทธิ์เข้าระบบใบขอซื้อ (e-HR → PR)

เอกสารนี้เขียนไว้ให้ฝั่ง **PR System** อ่าน · ฝั่ง e-HR ทำเสร็จแล้วใน **v1.6.20**

## สิ่งที่ e-HR รับผิดชอบ

| เรื่อง | รายละเอียด |
|---|---|
| ธงสิทธิ์ | `employees[].canAccessPR` เป็น **boolean** · ไม่มีฟิลด์นี้ = ไม่มีสิทธิ์ |
| ที่อยู่ของข้อมูล | `hr_data` key `employees` (ก้อน JSON เดิม) |
| ใครตั้ง | Admin เท่านั้น ที่ จัดการพนักงาน → แก้ไขพนักงาน → ระบบใบขอซื้อ |
| ค่าเริ่มต้น | `false` — พนักงานใหม่ไม่มีสิทธิ์จนกว่าจะเปิดให้ |
| การตัดสิทธิ์ | ปิดบัญชี (`active: false`) ถือว่า**ตัดสิทธิ์ทันที** แม้ `canAccessPR` ยังเป็น true |
| ทางเข้า | หน้า login มีตัวเลือกระบบ (เปิด/ปิดได้ที่ ตั้งค่า → ระบบ) · เมนูลัดใน e-HR สำหรับคนที่มีสิทธิ์ |
| บันทึก | เลือกไป PR แล้วจะมี audit `login-pr` |

## สิ่งที่ฝั่ง PR ต้องทำ

1. **คัดลอกสิทธิ์เข้า `pr.profile`** ไม่อ่าน `hr_data` สด (กฎเดิมในเอกสารออกแบบ) — ตัวซิงก์ควรเป็นฟังก์ชันใน Postgres ที่อ่าน `hr_data` แล้ว upsert `pr.profile` ทั้งสองแอปจึงไม่ต้องรู้จักกัน
2. **เงื่อนไขสิทธิ์ที่ต้องใช้ตอนซิงก์**
   ```
   มีสิทธิ์ = (employees[].active !== false) AND (employees[].canAccessPR === true)
   ```
   ถ้าไม่เข้าเงื่อนไข ให้ **ลบ/ปิด** แถวใน `pr.profile` ไม่ใช่ปล่อยค่าเก่าไว้
3. **บังคับด้วย RLS ของ schema `pr`** — ตัวเลือกบนหน้า login ของ e-HR เป็นแค่ความสะดวก ใครพิมพ์ URL ของ PR ตรง ๆ ก็เข้าถึงหน้าเว็บได้ กำแพงจริงต้องอยู่ที่ฐานข้อมูล
4. **ความถี่ของการซิงก์** ถ้าใช้ pg_cron อย่าลืมว่ามันรันเป็นเวลา GMT · การตัดสิทธิ์คนที่ลาออกควรเร็วกว่ารอบปกติ (เรียก RPC ตอน login ของ PR ก็ได้)

## ข้อจำกัดที่ยังอยู่

- **เซสชันไม่ข้ามโดเมน** ถ้า PR ไม่ได้อยู่โดเมนเดียวกับ e-HR พนักงานจะต้องล็อกอินใหม่อีกครั้งที่ PR (ตั้งค่า URL ได้ที่ ตั้งค่า → ระบบ → ระบบใบขอซื้อ)
- **ลำดับที่ตั้งใจไว้** ถ้ารหัสผ่านยังอ่อนเกินเกณฑ์ ระบบจะบังคับเปลี่ยนรหัสก่อนเสมอ แล้วค่อยเข้าระบบ — คนรหัส `1234` จึงข้ามไป PR ไม่ได้
- **คนที่ยังไม่มีบัญชี Supabase Auth เข้า PR ไม่ได้** (16 ต.ค. เหลือ 11 คน — ดู `db/verify/127_auth_missing.sql`) · ตั้งแต่ v1.6.21 **แอดมินกดรีเซ็ตรหัสผ่านให้ก็สร้างบัญชีให้เลย** ไม่ต้องรอให้พนักงานล็อกอินเอง
